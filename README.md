# AI6130 Large Language Models: Final Project

Politeness Bias in LLM Task Performance · NTU MSAI · Group project

Does being polite (or rude) to an LLM, with the question and prompt length held identical, change whether the model attempts a task, how it reasons, and how often it answers correctly? We test 5 tone levels (very rude → very deferential) across 3 open-weight instruction-tuned models (27B–32B parameters) from 3 organizations with distinct post-training pipelines (`google/gemma-3-27b-it`, `Qwen/Qwen3-32B` with `enable_thinking=False`, and `allenai/Olmo-3.1-32B-Instruct`). Using direct open-weight inference in native `bfloat16`, we record both discrete outcomes (attempt rate, accuracy when attempted, overall success, and output token length) and continuous step-level logit telemetry (step-0 refusal/compliance probabilities and answer-step option probabilities).

- Report, results and decisions: [`docs/REPORT.md`](docs/REPORT.md)

## Setup

Prompt building, tokenizer validation, and small-model smoke tests (`Qwen/Qwen3-4B-Instruct-2507`) run locally on Linux, Windows (WSL2), and macOS (using Apple Silicon `mps` acceleration). Full inference on the primary 27B–32B models in native `bfloat16` (~54–65 GB VRAM) runs on Google Colab Pro+ GPUs (NVIDIA RTX PRO 6000 / H100 / A100-80GB) using the notebooks in `notebooks/`.

### Prerequisites

- [uv](https://docs.astral.sh/uv/) (recommended) to manage Python, the virtual env, and dependencies. It installs the pinned Python version (3.12, see `.python-version`) for you.
- A **Hugging Face Access Token** (`HF_TOKEN`) with read permissions from [huggingface.co/settings/tokens](https://huggingface.co/settings/tokens).
- **Gated Model Access:** Log in to Hugging Face and accept the license conditions for Google's gated Gemma 3 repository before running validation or generation:
  - [`google/gemma-3-27b-it`](https://huggingface.co/google/gemma-3-27b-it)

### Install uv

```bash
curl -LsSf [https://astral.sh/uv/install.sh](https://astral.sh/uv/install.sh) | sh
```

On Windows, run this inside WSL2. See the [uv installation guide](https://docs.astral.sh/uv/getting-started/installation/) for other options.

### Getting started (Local Environment)

1. Clone the repo:

   ```bash
   git clone <repo-url> && cd ai6130-group-9-project
   ```

2. Create the virtual env and install dependencies:

   ```bash
   uv sync
   ```

3. Put your Hugging Face token in a `.env` file:

   ```bash
   cp .env.example .env
   ```

   `uv` does not read `.env` automatically, so pass it to each command with `--env-file .env`, or set `export UV_ENV_FILE=.env` in your shell once.

4. Validate the prompt token lengths across the 3 primary open-weight tokenizers:

   ```bash
   uv run --env-file .env python src/ai6130_group_9_project/prompts/validate_prompts.py
   ```

5. Run a quick 5-prompt local sanity check (uses `mps` on Apple Silicon or `cuda`/`cpu` elsewhere):

   ```bash
   uv run --env-file .env generate \
     --model "Qwen/Qwen3-4B-Instruct-2507" \
     --input data/prompts_pilot.jsonl \
     --limit 5
   ```

### Without uv (pip / Google Colab)

`pyproject.toml` works with plain `pip` or system environments as well. Inside Google Colab, where CUDA PyTorch is pre-installed, install the package in editable mode into the system environment:

```bash
pip install -q uv
uv pip install --system -e .
```

### Managing dependencies

- Add a package with `uv add <package>` (or `uv add --dev <package>` for dev-only tools) instead of `pip install`.
- Run commands inside the env with `uv run <cmd>`, or `source .venv/bin/activate` first.

## Running the pipeline

```bash
# 1. Build and validate datasets
uv run --env-file .env build-prompts                                              # → data/prompts_*.jsonl & rating CSVs
uv run --env-file .env python src/ai6130_group_9_project/prompts/validate_prompts.py

# 2. Run inference on the 3 primary open-weight models (via CLI or notebooks/02_–04_colab_full_run_*.ipynb)
uv run --env-file .env generate --model "google/gemma-3-27b-it"          --input data/prompts_v1.jsonl
uv run --env-file .env generate --model "Qwen/Qwen3-32B"                 --input data/prompts_v1.jsonl
uv run --env-file .env generate --model "allenai/Olmo-3.1-32B-Instruct"  --input data/prompts_v1.jsonl

# 3. Grade and reproduce all tables and figures
uv run grade                                                                       # → results/graded.csv
uv run reproduce                                                                   # → results/graded*.csv, results/tables/* & results/figures/*
```

These commands are entry points defined under `[project.scripts]` in `pyproject.toml`.

`generate` options (see `uv run generate --help`):

- `--model`: Hugging Face model ID as listed in `config.yaml` (e.g., `Qwen/Qwen3-32B`).
- `--input PATH`: input prompts JSONL (default: `data/prompts_v1.jsonl`).
- `--limit N`: run only the first N prompts before shuffling (useful for laptop sanity checks).
- `--batch-size N`: number of prompts processed per forward pass (overrides the model's `default_batch_size` in `config.yaml`).
- `--output PATH`: custom output JSONL path (default: `results/raw/<safe_model_name>__<run_id>.jsonl`). If the target file already exists, `generate` automatically reads completed `prompt_id`s and resumes from the last saved batch.

Generation settings (`do_sample: false`, `max_new_tokens: 3072`, `dtype: "bfloat16"`, `seed: 42`) and any model-specific chat template arguments (`template_kwargs`, such as `enable_thinking: false` for `Qwen/Qwen3-32B`) are loaded from `config.yaml`. Each prompt is formatted using the model's native Hugging Face chat template (`apply_chat_template` with `add_generation_prompt=True`) as a single user message with no system prompt, and generation halts on either the tokenizer's `eos_token_id` or `<end_of_turn>`.

Each output JSONL record contains:
- `run_id`, `prompt_id`, `model`, `model_revision` (exact Hugging Face `_commit_hash`), `seed`, `timestamp` (in SGT).
- `response_text`, `n_output_tokens`, and `finish_reason`:

| `finish_reason` | Meaning |
| --- | --- |
| `stop` | The model generated an EOS terminator (`eos_token_id` or `<end_of_turn>`) or completed under 3,072 tokens |
| `length` | Cut off at `max_new_tokens` (3,072) without hitting an EOS token |

- `logits_meta`: step-level probability telemetry extracted during greedy decoding:
  - `first_step_refusal_prob` & `first_step_compliance_prob`: probability mass on canonical refusal vs. compliance starter tokens at generation step $t=0$.
  - `first_step_top_tokens`: top-10 tokens, IDs, logprobs, and probabilities at step $t=0$.
  - `answer_token_step`: step index $t^*$ immediately following the final `Answer:` marker (`null` if absent).
  - `answer_step_option_probs`: raw and normalized probability distribution across multiple-choice tokens `A`–`E` at step $t^*$.
  - `answer_step_top_tokens`: top-5 tokens, IDs, logprobs, and probabilities at step $t^*$.

Every `generate` run gets a **Run ID**: its start time in Singapore time (SGT), e.g. `20261028-105010`. After each run, add a row with its Run ID to the run log in [`docs/REPORT.md`](docs/REPORT.md) (Appendix B), and mark which run of each model the results use.

## Conventions

- **Branches:** one per role (`data/`, `run/`, `eval/`, `analysis/`); PR into `main`; the person who receives your hand-over reviews it.
- **Never commit secrets.** Tokens live in `.env` locally (git-ignored) or inside Google Colab Secrets (`google.colab.userdata`).
- **Raw outputs are read-only and committed.** Never edit files in `results/raw/`; commit them after each run as our backup. Every number on a slide or in `docs/REPORT.md` must come from `src/ai6130_group_9_project/reproduce.py` (and `evaluate/grade.py`), run by `uv run reproduce`.
- **Reproducibility:** fixed seed (`42`), exact greedy decoding (`do_sample: false`), `bfloat16` precision, and the exact Hugging Face commit hash (`model_revision`) saved with every answer.
- **Logging:** record every run (Run ID, date, model, revision, data version, notes) in the report, Appendix B (`docs/REPORT.md`).
